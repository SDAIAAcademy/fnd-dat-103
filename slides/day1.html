Do not announce a winner: each row is a trade. Ask: which of these does a charger, appending one session at a time, care about? (Append.) Which does an analyst summing a month care about? (Types, columns.) Lab 1.1 measures what the table claims.

Sources: RFC 4180; RFC 8259 and jsonlines.org; the Apache Parquet file format documentation.

Delimited files

A CSV without its dialect is half a file

staff_code;grade;allowance;note
0042;B2;1250,50;"ترقية، ""مؤقتة"""
0107;A1;980,00;
  • Delimiter: here a semicolon, because the comma is the decimal mark.
  • Quoting: a field holding the delimiter or a quote is enclosed in quotes; an inner quote is doubled.
  • Encoding, line ending: not in the file; someone must say them.
  • Types: not in the file: "0042" is a code, not 42.
What goes wrong. A reader with the default dialect splits the note at its comma and turns the staff code into the number 42.

This is a parallel example from another department (payroll), not the lab's data. Walk through each setting and ask what pandas would do with defaults: comma delimiter, so one column; then with sep=";" the code becomes an integer unless dtype=str. RFC 4180 writes the quoting rules: fields with commas, quotes or line breaks are enclosed in double quotes; an inner double quote is escaped by another double quote.

Sources: RFC 4180, section 2.

JSON and JSON Lines

JSON Lines is one record per line, and that changes everything operational

One JSON document

An array of a million objects: one opening bracket, one closing bracket.

To add a record, rewrite the file. A cut at byte 900,000 makes the whole file invalid.

JSON Lines

One complete JSON value per line, UTF-8, a newline after each.

Append a line; stream it line by line; a damaged line loses one record, not the file.

Still text. Every line repeats every key, and numbers and times are written as text: large on disk, and a reader must parse each value back.

Ask why chargers and API clients like JSON Lines: they write as they go and can resume. Ask what it costs: size and parsing. Lab 1.1 measures both. The JSON Lines site requires UTF-8 and one valid JSON value per line.

Sources: RFC 8259; jsonlines.org.

Columnar files

A columnar file stores each column together, typed and compressed

Filea footer with the schema and where everything is
→
Row groupsblocks of rows, e.g. 100,000 sessions each
→
Column chunksone per column per row group, with min and max
→
Pagesencoded and compressed values
  • A query that needs two columns reads two chunks per row group, not every byte.
  • Statistics let a reader skip row groups whose range cannot match.
  • Similar values side by side compress well: codes, dates, small numbers.

Draw the contrast with a row file: to sum energy in a CSV you read every field of every line. Parquet's footer is why a reader knows the types without guessing. Keep the vocabulary: row group, column chunk, page, footer. Sources: Apache Parquet file format documentation; DuckDB documentation on reading Parquet (filter pushdown with min and max statistics).

Partitions

A partition is a folder per value, so a reader opens only what it needs

day=2026-10-19/part-0.parquet
day=2026-10-20/part-0.parquet
day=2026-10-21/part-0.parquet
...
  • The value lives in the folder name (the "hive" style), not inside the files.
  • A query for one day reads one folder.
  • Choose a column people filter on, with tens to hundreds of values, not millions.
What goes wrong. Partitioning by session id writes one tiny file per session: thousands of files and slower reads.

Ask which column the finance controller filters on most: the day, or the month. Station is a candidate too (40 values). The stretch of lab 1.1 writes this layout and lab 2.2 uses it for real. Source: Apache Arrow Python documentation, datasets and partitioning.

In memory

Arrow lets two tools share a table in memory, with no file between them

import duckdb, pyarrow.parquet as pq

loans = pq.read_table("loans.parquet",
                      columns=["branch", "items"])
duckdb.sql("""SELECT branch, sum(items)
              FROM loans GROUP BY branch""")
  • Arrow is a columnar layout in memory, as Parquet is on disk.
  • DuckDB finds the Python variable loans and queries it as a table.
  • No CSV in between: the types arrive as they left.

Parallel example: a library's loans table, not the charging data. Run it live if you have a Parquet file at hand; otherwise show it and let lab 1.1 do it. Point out the column selection at read time: the other columns are never read from disk. Sources: Apache Arrow Python documentation; DuckDB documentation, SQL on Apache Arrow and reading Parquet.

Measuring

Compare formats on three measures, taken the same way

Size

Bytes on disk. Stable: the same data gives the same size.

Read time

The median of several reads on one machine. It moves with the machine, the cache and the run.

Type fidelity

Column by column: same type and same values after a round trip with default readers.

What goes wrong. One timing quoted as a property of a format. Report the machine and the median, and trust sizes and fidelity more than seconds.

"Default readers" is deliberate: it is what a colleague will do with your file. Fidelity means equal values, not "looks the same when printed": an equality check or a hash sees differences a printout hides. Leave the findings for the lab.

Bytes and characters

A file holds bytes; text is bytes plus an agreed encoding

The word سلام inBytesPer letter
UTF-8d8 b3 d9 84 d8 a7 d9 852
Windows-1256 (cp1256)d3 e1 c7 e31
ISO-8859-6d3 e4 c7 e51
UTF-16 (little-endian, with its mark)ff fe 33 06 44 06 and so on2

Same four letters, four byte sequences. Nothing in the bytes says which table to use: the encoding is an agreement outside the file. UTF-8 is the default everywhere today; the two single-byte code pages survive in old Arabic systems and exports. These bytes were computed with Python's codecs (labs run the same library).

Sources: Python documentation, codecs, standard encodings.

Legacy Arabic code pages

Read a legacy file as UTF-8 and it fails; read UTF-8 as legacy and it lies

cp1256 bytes read as UTF-8

A UTF-8 decoder meets single high bytes it cannot use: an error, or ���� with errors="replace". Loud, at least.

UTF-8 bytes read as cp1256

cp1256 maps every byte to a character, so it never fails: سلام reads as ط³ظ„ط§ظ…. Quiet, and wrong.

Saved again, it sticks. Write that wrong text back as UTF-8 and the file is now double-encoded: valid UTF-8, nonsense Arabic. Undo it by reversing the wrong step: encode as cp1256, decode as UTF-8.

The signature of double-encoded Arabic is runs of two-character pairs that start with the same few letters. Demonstrate in a Python cell: "سلام".encode().decode("cp1256") and back. Ask why the second case is worse: no error, so no one notices until a report shows nonsense names.

Byte order marks

A byte order mark is invisible text at the start of a file

  • ef bb bf: the UTF-8 mark, added by some editors and spreadsheet exports.
  • ff fe or fe ff: the UTF-16 marks, which say the byte order.
  • Read as plain UTF-8, the mark becomes the character ﻿ glued to the first column name.
df = pd.read_csv("grades.csv")
df["student_code"]   # KeyError
df.columns[0]        # '﻿student_code'
pd.read_csv("grades.csv",
            encoding="utf-8-sig")

Parallel example: a school's grades export. The KeyError on a column you can see is the classic symptom. utf-8-sig removes the mark if present and reads plain UTF-8 otherwise, so it is safe as a default for files from spreadsheet tools. A UTF-16 file shows a zero byte after every ASCII letter.

Diagnosis

Detection is a guess; confirm it with a word you know

1 · Lookthe first bytes in hex: a mark, zero bytes, single high bytes
→
2 · Trydecode with the likely encoding
→
3 · Confirma value you know must appear, such as a station or branch name
→
4 · Recordthe encoding in the load log
Rule. "It opened without an error" proves nothing for a single-byte code page: every byte decodes to something.

This is the routine lab 1.2 asks for, file by file, with the diagnosis written before any repair. Encoding-detection libraries exist and are useful, but they return a probability: the confirmation step is still yours.

Offsets and UTC

A time without an offset is a guess about someone's clock

Written asMeans
2026-11-02T09:00:00+03:0009:00 on a clock three hours ahead of UTC
2026-11-02T06:00:00ZThe same instant, in UTC
2026-11-02 09:00Unknown: which clock?
  • RFC 3339 times carry Z or +hh:mm: the instant is fixed.
  • Store instants in UTC, keep the offset when it matters, convert to local time only to display.

The network's local time is UTC+03:00 all year, with no daylight saving. A device configured for another zone, or a developer who assumed UTC, shifts every session by a whole number of hours. Ask: how would you notice? Compare with a source you trust that does carry offsets.

Sources: RFC 3339, section 5.6.

Daylight saving

Daylight saving skips one hour in spring and repeats one in autumn

Spring: a missing hour

In the CET zone, on 29 March 2026, clocks jump from 02:00 to 03:00. A log line at 02:30 names a time that never happened there.

Autumn: a repeated hour

In the EET zone, on 26 October 2025, 03:30 happens twice: first at 00:30 UTC, then at 01:30 UTC.

In Python. zoneinfo marks the second pass of a repeated time with fold=1. Without another clue, such as the order of events, nobody can tell which pass a bare time meant.

Run it: datetime(2025, 10, 26, 3, 30, tzinfo=ZoneInfo("EET"), fold=0) has offset +3, fold=1 has +2. Ask what clue would tell the passes apart in a log: a sequence number, an event counter, or the previous line's time. Lab 1.2 meets this with another zone and another vendor. Python compares two times of the same zone by their clock reading and ignores fold: convert to UTC before comparing. CET and EET are short legacy names that the time-zone database still carries (as links to region zones since its 2024b release); real code should name the region zone a device actually uses.

Sources: Python documentation, zoneinfo (fold); the IANA time-zone database through the tzdata package.

Checkpoint

What happened to the catalogue file?

A public library's catalogue export opens in UTF-8 without any error, but its Arabic titles read as long runs of pairs like ط§ظ„. What happened?

It is in cp1256 and was read as UTF-8
It starts with a UTF-8 byte order mark
It was decoded as cp1256 once and saved again as UTF-8
It was saved as UTF-16
Why. Valid UTF-8 with nonsense Arabic is the signature of double encoding: the bytes were decoded with the wrong table once, and the wrong text was stored.

Answer: double encoding. The repair reverses the wrong step: encode as cp1256, decode as UTF-8. If the room splits between the first and third options, return to the "fails or lies" slide: the error is the difference.
