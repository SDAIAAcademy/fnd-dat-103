Review of Day 1

Which fault is this?

A water utility's meter readings, logged without offsets, run exactly 240 minutes ahead of the billing system's UTC times on every day of the year. What is the fault?

A clock in a zone that has daylight saving time
A file saved in a legacy code page
A CSV that lost the column's type
A clock on a fixed offset, read as UTC
Why. A gap that never changes is a fixed offset: localise every time to that offset and convert to UTC.

Answer: a fixed-offset clock read as UTC. If anyone picks daylight saving, ask what the gap would do on the day the clocks change. Two minutes, then session 3.

01
HTTP in one slide

A request names what you want; the status says what happened

requestGET /v1/stations?limit=50&cursor=Yz0x with Authorization: Bearer ...
status200 OK
headersContent-Type: application/json
body{"data": [...50 items...], "next_cursor": "Yz01MA"}

Read the status before the body: a 429 or a 500 may carry an HTML page, not your JSON.

This is a generic example, not the lab's API. Ask what a client that calls .json() on every response does when the body is an HTML error page: it crashes far from the cause. Lab 2.1 shows exactly that with a plain client.

Sources: RFC 9110, HTTP semantics.

Status codes

Each status asks the client for a different action

StatusMeansThe client
200Here is the dataUses it
400 401 403 404The request is wrong or not allowedStops and reports: repeating will not help
429Too many requestsWaits as long as Retry-After says, then repeats
500 502 503 504The server failed, often brieflyWaits longer each time, then repeats; gives up after a few tries

RFC 6585 defines 429 and says the response may include Retry-After, which RFC 9110 defines as seconds or a date. A 4xx other than 429 is about your request; retrying it adds load and can lock a token. Ask for one example from the room of a 404 that is not an error (a page past the end).

Sources: RFC 9110; RFC 6585, section 4.

Pagination

An offset is a position; a cursor is a bookmark

Offset: "skip 100, give me 100"

Newest first, five new items arrive after page 1. Every older item moves down five places, so page 2 starts with five items you already have, and the five new ones are never seen in this pull.

Cursor: "after the last one I saw"

The server returns an opaque token naming the last item. New items at the top do not move what comes after it; the next run picks them up.

What goes wrong. Offset paging fails silently: no error, just repeats and gaps that a count by id would reveal.

Draw it on the board with a list of ten numbered items and a page size of three. Insert two at the top after the first page and let the room find the repeats. Offset paging is fine for a list that does not change while you read it; most live lists change.

Retries

Back off exponentially, add jitter, and stop after a few tries

Try 1
0.5 s
Try 2
1 s
Try 3
2 s
Try 4
4 s
Try 5
8 s
  • Wait = base × 2try − 1, capped, plus a small random jitter.
  • Jitter spreads clients that failed together, so they do not return together.
  • A 429 with Retry-After overrides the formula.

The waits shown are the formula with a base of half a second, before jitter. In the lab the client calls sleep through a parameter: the notebook passes a fake clock that records waits instead of waiting, so a run with minutes of backoff takes seconds and the log shows every wait. That is also how you test retry code.

Rerunnable loads

Write records by key, then the checkpoint: a crash anywhere is safe

1 · Fetchthe page after the saved cursor
→
2 · Save rawthe page as it came
→
3 · Write by idskip ids already kept
→
4 · Checkpointthe next cursor
  • A crash before step 4 means the page is fetched again; step 3 makes that harmless.
  • "Exactly once" is proven by counting: records equal unique ids equal the source's count.

The worst moment to crash is after writing and before checkpointing: the lab stops the run exactly there. Idempotent means doing it twice has the same effect as once. Ask what would happen with an append-only write and no id check: duplicates on every resume.

Tokens

A token belongs to a person and the environment, never to the code

import os

# set in the shell, or in .env (excluded by .gitignore)

  • A token pasted in a notebook stays in its history and every copy.
  • Tokens are issued per person by the data's owner, who can revoke them.

The course's mock token in .env.example is a course value that opens only the mock. Segregation of duties: the person who writes the client does not issue or hold the production token; the platform owner issues one per person and revokes it. The lab checks that no saved page or log line contains the token.

Respectful collection

Read the terms and limits before the first request

  • Rate limits: stay under them; honour 429 and Retry-After.
  • Licence: what you may keep, share and publish, and how to credit the source.
  • Retention: how long raw responses may be kept.
  • No published limit is not permission: set your own pace, write it in the code, and say it is yours.
In the lab. The public API task reads the series' licence from its metadata and stops unless it is open; it then paces itself at one request a second, the course's own rule.

The public API of the lab, the World Bank Indicators API, needs no key, pages by number and records a licence per series; its datasets terms say CC BY 4.0 unless labelled otherwise. It publishes no rate limit, so one request a second is the course's rule, not the provider's. Nothing it returns is stored in the course.

Sources: World Bank, API basic call structures; World Bank terms of use for datasets.

Checkpoint

Which response should the client retry?

A pull from a weather-station network's API gets these four answers on different pages. Which one should it retry after a wait, with no change to the request?

503 Service Unavailable
400 Bad Request: "limit must be at most 200"
401 Unauthorized
404 Not Found for one station
Why. A 503 reports a temporary failure of the server: the same request can succeed later, after a backoff.

Answer: 503. The 400 needs a change to the request (a smaller limit), then it is a new request, not a retry. If the room picks 401, return to the tokens slide.

02
Flattening

Nested JSON becomes one table per grain, with the key carried down

{"visit_id": "V-0193",
 "clinic": {"id": "C04", "floor": 2},
 "booked_at": "2026-11-03T08:40:00+03:00",
 "tests": [{"code": "T-11", "result": 5.4},
           {"code": "T-27", "result": 0.9}]}
  • Once per visit (the clinic object): columns of the visits table, clinic_id, clinic_floor.
  • A list (the tests): its own table, one row per test, with visit_id on every row.
  • Count after flattening: visits equal records; tests equal the sum of list lengths.

Parallel example: a clinic visit with its tests, not the lab's charging sessions. Ask what goes wrong with columns test_1, test_2, test_3: a visit with four tests. Ask what goes wrong with one row per test and the clinic repeated: the visit's own numbers are counted once per test when summed.

Declared types

Declare the schema in code, and cast to it before writing

import pyarrow as pa

VISITS = pa.schema([
    pa.field("visit_id", pa.string(), nullable=False),
    pa.field("clinic_id", pa.string(), nullable=False),
    pa.field("booked_at", pa.timestamp("us", tz="UTC"), nullable=False),
    pa.field("month", pa.string(), nullable=False),   # the partition column
])
table = pa.Table.from_pandas(visits, schema=VISITS, preserve_index=False)
  • A value that cannot be cast fails here, at the boundary, not in next month's report.

Point at the time zone in the type: a timestamp column that says UTC cannot silently hold local times. Nullable=False turns "missing" into an error at cast time. Source: Apache Arrow Python documentation.

Proof

Prove the files match the declaration by reading their schema back

1 · Writepartitioned by the declared column
→
2 · Read the schemaof one written file
→
3 · Comparewith the declaration, minus the partition column
→
4 · Countrows read back from the whole folder
Why minus one column. In hive partitioning the partition value lives in the folder name; readers add it back as a column.

This is the evidence of LO4: files whose schema matches the declared one. Printing rows is not proof: two time zones or a float and a decimal can print alike. pyarrow.parquet.read_schema reads only the footer, so the check is cheap.

Validation

Check each record, then check the table

LayerRulesExample tool
Record, one at a timeRequired fields, types, patterns (a time with its offset), allowed valuesJSON Schema
Table, the batch as a wholeUnique keys, ranges, one column against another, values that must exist in a registerPandera
  • Record checks run before flattening, on the raw JSON.
  • Table checks run on the typed table, after the cast.

A primary key in a database (FND-DAT-101) is one kind of table check; here the checks run before anything reaches a database. Tools are examples: plain assertions in Python fill the same slot for a small batch. Sources: JSON Schema specification; Pandera documentation.

Record checks

A JSON Schema states what one record must be

{"type": "object",
 "required": ["visit_id", "clinic", "booked_at", "tests"],
 "properties": {
   "visit_id": {"type": "string", "pattern": "^V-[0-9]{4}$"},
   "booked_at": {"type": "string",
     "pattern": "^[0-9-]{10}T[0-9:]{8}(Z|[+-][0-9]{2}:[0-9]{2})$"},
   "tests": {"type": "array", "minItems": 1}}}
  • Each error names its rule (required, type, pattern) and its path: the report's reason.

Parallel example: the clinic visits. Show jsonschema's iter_errors on a record with booked_at cut to "2026-11-03T08:40:00": one pattern error at path booked_at. A schema is a document: version it, and add optional fields without breaking old senders (the lab's stretch).

Table checks

Named table checks give every failing row a reason

import pandera.pandas as pa

checks = pa.DataFrameSchema(
    {"visit_id": pa.Column(None, pa.Check(lambda s: ~s.duplicated(keep=False), name="duplicate_key")),
     "clinic_id": pa.Column(None, pa.Check(lambda s: s.isin(CLINICS), name="unknown_clinic"))},
    checks=[pa.Check(lambda df: df["seen_at"] >= df["booked_at"], name="seen_before_booked")])
checks.validate(visits, lazy=True)   # raises SchemaErrors listing every failure

lazy=True collects every failure instead of stopping at the first; err.failure_cases has the check name and the row index, which is what a quarantine file needs. Name each check: built-in checks report a generated description, which is harder for an owner to read.

The decision

Reject the batch, or quarantine rows: decide by written rules

The interface changeda required field missing from nearly every record: reject the batch, name the field
↓
Some rows break the rulesquarantine each with its reason, keep the rest
↓
Too many rows breakabove the organisation's threshold: reject the batch
↓
Otherwiseload the valid rows

The thresholds are choices, not standards: the lab uses 90% for a changed interface and 5% for "too many", the case organisation's own rules. What matters is that they are written down and applied the same way every time. Ask why "too many" rejects even the good rows: the same fault may hide in rows that passed.

Quarantine

Quarantine so that owners see what failed, and fix it at the source

The loader

Writes each row with its rule and meaning; does not edit or release rows.

The data owner

Corrects the source and sends the rows again.

A second person

Reviews any release of quarantined rows.

Next. Data contracts, with versions and service levels between sender and receiver, follow in DEV-DAT-204.

Segregation of duties: whoever writes the checks should not also be the one who waives them. Deleting bad rows hides the fault from the people who can fix it; silently repairing them hides it too. The quarantine file is part of the responsible-use statement of this course.

Checkpoint

Load, quarantine or reject?

A library's loans batch has 400 rows. Twelve rows (3%) name a branch code that is not in the branch register; every other check passes. The written rules: reject on a changed interface, or above 5% quarantined.

Reject the whole batch
Map the twelve codes to the nearest valid branch and load all
Load 388 rows and quarantine 12 with their reason
Load 388 rows and drop the 12
Why. 3% is under the written threshold, so the valid rows load and the twelve go to the branch team with the reason, to fix at the source.

Answer: load 388, quarantine 12. If the room picks "map to the nearest branch", ask who signs off that guess. If it picks "drop", ask how the branch team would ever learn.
